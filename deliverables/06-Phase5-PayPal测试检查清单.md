## 1. T-5.1 — 3DS / SCA 真实欧洲卡测试（预估 1d）

> 为什么单列：欧洲 PSD2 法规强制 SCA。sandbox 测试卡直接跳过挑战页，生产里跳 3DS 的卡
> 在欧洲会被拒付，买家流失 + 拒付率上升会反过来影响 PayPal 对商户的风险评级。

**前置**：PPCP 插件已开 Advanced Card Processing（ACDC 信用卡直收），且为最新版
（旧版存在「3DS 挑战完成后 capture 不立即执行」的 bug，见 05 清单排查表）。

| # | 用例 | 步骤 | 通过标准 | 结果 |
|---|---|---|---|---|
| 1.1 | 真实欧洲 Visa 走 3DS 挑战 | 用一张真实签发的欧洲 Visa（个人卡即可，金额 $5–10）下单付款 | 浏览器弹出 3DS 挑战页（短信/App 验证码）→ 完成后付款成功；**不允许跳过挑战直接付款成功** | ☐ |
| 1.2 | 3DS 挑战中取消 | 在挑战页点取消/关闭 | 订单停在失败态，前端提示清晰，可重试；不会产生已扣款但订单 pending 的孤儿单 | ☐ |
| 1.3 | 挑战成功后的状态流转 | 完成 1.1 后观察 WP 后台 | 订单 `pending → on-hold → processing` **全自动**，无需手动 capture；确认邮件（Noir 品牌版）发出 | ☐ |
| 1.4 | 英国卡（非 EEA 但 SCA 普及） | 用 UK 卡付一笔 | 同 1.1–1.3 | ☐ |
| 1.5 | 挑战失败（错验码） | 故意输错 3DS 验证码 | 付款失败，可重试；订单不卡死 | ☐ |

⚠️ 每笔都记录：卡种 / 发卡国 / 订单号 / PayPal 交易号 / 挑战页截图。

## 2. T-5.2 — 多币种真实汇率测试（预估 0.5d）

> ⚠️ 本项目的前提：CURCY 配置了 `pmcs_cart/checkout_default_currency=yes`
> （**结账恒走基准 USD**，这是 PayPal 不拒单的安全前提，已实测）。
> 所以这里测的不是站内多币种结账，而是 **PayPal 侧的钱包币种转换**。

| # | 用例 | 步骤 | 通过标准 | 结果 |
|---|---|---|---|---|
| 2.1 | 欧洲买家 EUR 钱包买 USD 商品 | 切站点语言到 de/es（前台显示 € 只是展示价），用 EUR 余额的 PayPal 账户付款 | 结账请求金额为 USD（容器日志确认）；PayPal 向买家扣 EUR；商户收入 USD | ☐ |
| 2.2 | 汇率损耗核对 | PayPal 后台打开该笔交易详情 | 买家侧汇率损耗 2.5–4% 属正常范围；记录实际值，反馈客户定价参考 | ☐ |
| 2.3 | 站内币种切换不破坏结账 | 带 EUR cookie 进结账（本地已验证 Store API 恒 USD）再付款 | 支付金额与订单金额一致，PayPal 不报币种不匹配错误 | ☐ |
| 2.4 | BRL（本地化最强）抽查 | 用 pt 界面 + 巴西卡走一遍 | 同 2.1 | ☐ |

## 3. T-5.3 — 风控触发 + 资金留存演练（预估 0.5d）

> 新商户账户前 90 天，PayPal 普遍对部分交易做资金留存（typically 21 天）。
> 这不是 bug，是流程——演练目的是让客户在收到第一笔真实订单前**亲眼见过一次**。

| # | 用例 | 步骤 | 通过标准 | 结果 |
|---|---|---|---|---|
| 3.1 | 高客单价测试单 | 下单一个 > $500 的商品（可用测试商品临时改价，测完改回），真实付款 | 全链路成功（付款 → processing → 邮件） | ☐ |
| 3.2 | 资金可用性检查 | PayPal 后台 → 该笔交易 → 查资金状态 | 若被留存：能看到明确的「available on date」（约 21 天后）。截图归档 | ☐ |
| 3.3 | 留存期间退款 | 对被留存的交易做全额退款 | 退款成功且不占用周转资金之外的部分；订单 → `refunded` | ☐ |
| 3.4 | 放款周期确认 | 若留存：设置日历提醒在 available on date 后复查 | 资金如期转入可用余额；把「预计放款日」同步客户 | ☐ |
| 3.5 | 客户知情确认 | 把 3.2/3.4 截图发给客户 | 客户书面确认理解（并入 B4 签收文档） | ☐ |

## 4. T-5.4 — 支付回调原子化压测（预估 1d）

> 目标：证明 webhook 回调链路「验签 → 验金额 → 状态流转 → 扣库存 → 发邮件」
> **幂等、抗重放、抗乱序、抗并发、可恢复**。这是四个任务里唯一能测出代码级 bug 的，
> 也是 PayPal 重试机制（失败后 24h 内按 1min→5min→…→16h 间隔重发）唯一能兜住的场景。

观察日志的命令（全程开着）：

```bash
docker logs -f woocommerce-wordpress-1 2>&1 | grep -iE "webhook|ppcp|capture"
```

| # | 用例 | 步骤 | 通过标准 | 结果 |
|---|---|---|---|---|
| 4.1 | **幂等/重放**：同一事件重发 | PayPal Dashboard → Webhooks → 已有成功的 `PAYMENT.CAPTURE.COMPLETED` → Resend，连发 2 次 | 订单状态不变（仍 processing）；邮件**不重发**；库存**不重复扣**；日志无错误 | ☐ |
| 4.2 | 手动模拟重放 | 用 PayPal Simulate Event 对生产订单触发同事件 | 同 4.1（PPCP 内部按 transaction ID 幂等） | ☐ |
| 4.3 | 拒付事件 | Simulate `PAYMENT.CAPTURE.DENIED` | 订单 → `failed`，前端有清晰提示；不扣库存 | ☐ |
| 4.4 | 退款事件 | 后台真实退款一笔 | webhook 收到 `PAYMENT.CAPTURE.REFUNDED` → 订单 → `refunded`；库存回补（如配置）；退款邮件发出 | ☐ |
| 4.5 | **并发回调**：3+ 订单同时付款 | 3 个浏览器隐身窗口（3 个买家会话）同时完成付款 | 每个订单各自正确流转，金额/地址/邮件零交叉污染 | ☐ |
| 4.6 | **回调中断恢复** | 付款成功瞬间 `docker compose restart wordpress` | 容器恢复后靠 PayPal 重试补齐：最终订单状态正确（允许延迟，不允许永久 pending）；`docker logs` 里能看到重试请求 200 | ☐ |
| 4.7 | 金额篡改防护 | 检查 PPCP 的 webhook 验签配置（production 下自动强制） | 伪造的 webhook（改金额/无签名）被拒：日志 401/400，订单不动 | ☐ |
| 4.8 | 库存原子性 | 4.1 + 4.5 后核对商品库存数 | 每笔成功付款恰好 -1；重放/并发不额外扣 | ☐ |
| 4.9 | 业务链回归 | 以上任一成功订单走完整业务流：processing → 后台标 pending-supplier → 加物流单号 → completed | 状态流转正确，客户邮件（品牌化+AST 追踪块）正常 | ☐ |

## 6. 失败排查速查

| 现象 | 最可能原因 | 排查 |
|---|---|---|
| PayPal 后台看不到 webhook 事件 | URL 不通 / 证书无效 | 浏览器 GET webhook URL 应返回 405 |
| 付款成功但订单停在 pending | capture 回调没走通 | 后台手动 Capture 试流转；检查日志里 webhook 是否到达 |
| 3DS 挑战后付款失败 | PPCP 旧版 capture bug | 升级 PPCP 到最新版重测 |
| 重放后邮件重发/库存重扣 | 幂等实现缺失 | 这是**代码级缺陷**，停下来修，不许绕过 |
| 高客单价订单付款被拒 | 新账户风控 | 换金额分拆测试；与 PayPal 客服确认账户状态 |

完整版见 05 清单「每一步卡住了怎么办」。
